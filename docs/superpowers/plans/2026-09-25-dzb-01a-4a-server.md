# DZB-01a-4a — the wire protocol and the WebSocket server — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Put the subscription engine on the network. A client subscribes to a named query and receives its value,
then one frame per flush cycle with every changed value. It calls a mutation and learns which cycle carries the
write. A boot helper wires Postgres, capture, runtime, engine and server, and restarts the capture when it fails.

**Architecture:** four pieces.
- `src/protocol/`: frames, a value codec, frame validation. It depends on nothing and is safe on the client.
- `src/server/`:
  - the API registry (`defineApi`: names → function definitions);
  - the WebSocket handler (`createHandler`: Bun `upgrade` + `websocket` handlers);
  - `startDrizzleBase` (the boot and capture-restart loop).
- `src/runtime/functions.ts` gains an optional `args` validator (Standard Schema).
- Everything is exported from `drizzle-base/server`.

**Spec:** `docs/specs/DZB-01-foundation.md`: POST-REVIEW phases table (01a: "functions, WebSocket and React client
(quarried)"), D9 (read-your-writes), D14 (fail closed: widen or refuse, never serve stale silently), P-A7, P-M6.

**Owner decisions (25 Sep 2026):**
- Three slices: 4a server, 4b client + React, 4c demo with Drizzle Studio. 01a-5 is the closing benches.
- A mutation resolves only once the client has received a transition at or after its cycle (Convex's semantics).
- The typed API has no codegen: the client imports the API's TYPE and uses a Proxy (tRPC's model).

## Decisions

- **D1. Frames.** JSON text frames. Every frame is an object with `t`.
  - Client → server:
    - `{t:"sub", id:string, name:string, args:object}`
    - `{t:"unsub", id}`
    - `{t:"mut", id, name, args}`
    - `{t:"ping"}`
  - Server → client:
    - `{t:"upd", id, value}`: the subscription's first value (its own fresh snapshot, `cycle: null` in the engine; provisional, see 4b)
    - `{t:"txn", c:number, u:[{id, value} | {id, error:{code, message?}}]}`: every change a cycle made for this connection, one frame
    - `{t:"res", id, value, c:number|null}`: `c` is null when the write committed but could not be confirmed (`CommittedUnconfirmedError`)
    - `{t:"err", id?:string, code, message?}`
    - `{t:"reset"}`: the engine reset; every subscription on this connection is gone
    - `{t:"pong"}`
  - Error codes: `bad_request`, `not_found`, `invalid_args`, `too_many_subscriptions`, `duplicate_id`, `unavailable`
    (the engine is down: retry), `app` (a `DrizzleBaseError`: its message and optional JSON `data` go out), `internal`
    (anything else: no message, logged with the frame id).
- **D2. Values.** `encodeValue` / `decodeValue` in `protocol/codec.ts` keep what JSON loses in Drizzle results:
  - `Date` → `{"$t":"date","v":iso}`
  - `bigint` → `{"$t":"bigint","v":"…"}`
  - `Uint8Array`/`Buffer` → `{"$t":"bytes","v":base64}`
  - `undefined` in an object → dropped; in an array → `null`, as JSON does
  - A plain object that has a `$t` key is escaped as `{"$t":"obj","v":{…}}`, so no application value can be
    mistaken for a tag.
  - Anything else that is not JSON (a class instance, a function, a symbol, a non-finite number) is refused by the
    encoder: an `internal` error for that call, never a silent `{}`.
- **D3. The registry.**
  - `defineApi(tree)` walks a nested object whose leaves are `QueryDef`/`MutationDef` and maps `"a.b.c"` → def.
  - It rejects at definition time:
    - a key containing `.`;
    - a leaf that is not a definition;
    - an empty tree.
  - It returns the tree unchanged, typed, plus a hidden registry, so `typeof api` is what 4b's client imports.
  - Only names in the registry are callable. A `sub` for a mutation, or a `mut` for a query, is `not_found`, the
    same answer as an unknown name (no probing by kind).
- **D4. Args.**
  - `args` must be a plain JSON object, or the frame is `bad_request`.
  - A definition may carry a Standard Schema `args` validator: `query({ args: schema, handler })`, next to today's
    `query(handler)`.
  - Validation runs before the handler, and before the engine sees the subscription. Its output (possibly
    transformed) is what the handler and the subscription key use.
  - A failure is `invalid_args` with the issues' messages.
  - Without a validator, the handler gets the decoded JSON as is. The docs say so.
- **D5. Per-connection transitions.**
  - Each subscription's engine listener writes `{id, value|error}` into the connection's buffer for the current
    cycle (`Map<clientId, entry>`: a later write in the same cycle replaces an earlier one).
  - On `onCycleComplete(n)`, every connection with a non-empty buffer gets one `txn` frame with `c:n`, and its
    buffer is cleared.
  - A connection with no changes but a pending mutation whose named cycle is ≤ n gets `{t:"txn", c:n, u:[]}`, so
    its client can resolve.
  - Invariant 6 holds per connection: one frame per cycle, all from one snapshot.
- **D6. Read-your-writes.**
  - `mut` runs `engine.mutate`. The reply is `res` with `c` = the named cycle. The connection records `c` as
    pending until a cycle ≥ c completes (D5).
  - The client (4b) resolves on the first `txn` with `c ≥ res.c`.
  - `res` is always sent before any `txn` with `c ≥ res.c` on that connection. The handler sends `res` right after
    `mutate` returns; the named cycle has not started then, because the engine names `started + 1`.
- **D7. Engine events.**
  - `value`/`error` with a cycle id go to the buffer.
  - `value`/`error` with `cycle: null` (a fresh or joined value) go out immediately as `upd` for the first event.
    A later null-cycle event, if the engine ever sends one, goes out as `upd` too.
  - `reset` → one `{t:"reset"}` per connection. The connection's subscription map is dropped without calling
    `off()` (the engine already forgot them).
  - A `sub` while the engine is down → `err` `unavailable`.
- **D8. Limits and slow clients (quarried from minivex).**
  - Per connection: `maxSubscriptions` (default 1000). Pending subscribes count too.
  - `maxPayloadLength` (default 1 MiB) and `backpressureLimit` (default 8 MiB).
  - A push that Bun reports as dropped (`send()` returns 0) closes the socket with 1013 "backpressure". The engine
    already considers the value delivered, so a dropped frame would leave the client stale forever.
  - `idleTimeout` 60 s; the client pings (4b).
  - A duplicate `sub` id → `duplicate_id`.
  - A message rate limit is NOT in 4a. It is recorded as a gap for 01a-5 / auth.
- **D9. Origins.**
  - `createHandler({ allowedOrigins })`: when set, an upgrade whose `Origin` is not listed is refused with 403.
  - Unset means any origin, which is acceptable only because 4a has no ambient authority (no cookies, no auth). The
    README states it. `@drizzle-base/auth` will require it.
- **D10. Close and cleanup.**
  - On close, every subscription's `off()` runs and the pending-mutation marker goes.
  - A mutation still running when its socket closes completes. Its reply is dropped, and it is never replayed.
- **D11. Boot: `startDrizzleBase({ connection, schema, api, names, port?, hostname? })`.**
  - Creates the pool (`prepare: false`), then `assertCapture` (boot fails closed if the publication or slot is
    wrong), the Runtime, the engine, the capture and the server.
  - On a capture error:
    1. `engine.reset(reason)`
    2. stop the capture
    3. `dropCapture` + `ensureCapture`: a new slot, so no snapshot predates it (P-M6)
    4. start it
    5. `engine.resume()`
    - It retries with backoff (250 ms doubling to 10 s) until it succeeds or `stop()` is called.
  - Returns `{ url, engine, runtime, stop() }`.
  - The default hostname is `127.0.0.1`. Binding anything else is the caller's explicit choice (the appsec rule
    against public-by-default resources).
- **D12. Logging.**
  - An `internal` error is logged with the function name and frame id, never with args or values.
  - The library has no logger yet: `console.error` is behind one `log()` in `server/log.ts` (the only
    `biome-ignore noConsole`), replaceable through the `onError` option.

## Tests (each property with its sabotage)

1. **Codec round-trip.**
   - `Date`, `bigint`, bytes, nested, `$t` escaping.
   - A user object `{"$t":"date","v":"x"}` comes back as that object. Sabotage: skip the escape → red.
   - The refusal of class instances and non-finite numbers. Sabotage: `JSON.stringify` fallback → red.
2. **Frame validation.** Every malformed client frame is `bad_request`: missing `t`, unknown `t`, non-string `id`,
   an `args` array, an oversized `id`. Sabotage: accept an array `args` → red.
3. **Registry.** Nested names, a key with a dot refused, a non-def leaf refused, kind confusion (`sub` on a
   mutation) → `not_found`.
4. **Subscribe and push (integration, a real engine + WS).**
   - `upd` first, then a raw-SQL insert → a `txn` with `c` and the new value.
   - `unsub` → no further frames for that id (premise: another sub on the same connection still gets its `txn`).
5. **One frame per cycle.**
   - Two subscriptions on one connection changed by one transaction → ONE `txn` carrying both, with one `c`.
   - Sabotage: send per listener → red.
6. **Read-your-writes on the wire.**
   - `mut` → `res{c}`, then a `txn` with `c' ≥ c` arrives even when the write changed nothing that connection
     watches (the stamp-only frame).
   - `res` precedes that `txn`.
   - 20 in a row, asserting each time that the value held at that `txn` contains the write.
   - Sabotages: no stamp-only frame → red; `res` sent after awaiting the cycle → the ordering assertion red.
7. **Errors.**
   - Unknown name → `not_found`.
   - Invalid args (Standard Schema: a tiny local schema object, no new dependency) → `invalid_args`.
   - A handler that throws `new Error("secret detail")` → `internal`, and the frame does NOT contain "secret detail".
   - `DrizzleBaseError("nope", {x:1})` → `app` with message and data.
   - Sabotage: forward `String(e)` → the secret assertion red.
8. **Limits.**
   - Sub number `maxSubscriptions + 1` → `too_many_subscriptions`.
   - A duplicate id → `duplicate_id`.
   - Over `maxPayloadLength` → the socket closes.
   - Backpressure: a unit test of `pushOrClose` with a fake socket whose `send` returns 0 → `close(1013)`.
   - A disallowed Origin → 403, with no upgrade.
9. **Cleanup.** Close the socket → `engine.size` drops back to its value before (premise: it rose with the subs).
   Sabotage: skip `off()` → red.
10. **Reset.** `engine.reset` → the client gets `reset`. `sub` while down → `unavailable`. After `resume`, a new
    `sub` works.
11. **Boot restart (integration).**
    - `startDrizzleBase` on the test database.
    - A subscriber connected; `pg_terminate_backend` of the walsender → the subscriber receives `reset`.
    - Within 10 s a new `sub` succeeds, and a raw write re-pushes it. That proves the capture restarted and the
      engine resumed.
    - Sabotage: skip `resume` → red.
12. **Args validation.** A `{args, handler}` definition: a valid call passes the transformed output; an invalid
    one never reaches the handler (premise: a handler counter stays 0).

## Risks

- **Engine listeners run synchronously inside the push loop.** A slow socket write there would stall the cycle.
  Writes go to a buffer; the actual `send` happens once per connection in `onCycleComplete`, which is still inside
  the cycle. Bun's `send` does not block (it queues up to `backpressureLimit`).
- **A client that never reads.** `backpressureLimit` plus close-on-drop bounds the server's memory per client.
- **Hash-of-args keys.** The engine keys subscriptions by `stableHash(args)`. Args come from the validator's
  output, so two equivalent inputs share an entry only if the validator normalises them. That is acceptable.
- **Test flakiness.** The integration tests hold a real engine; every wait is event-driven (`next(pred)` with a
  deadline), never a bare sleep.
